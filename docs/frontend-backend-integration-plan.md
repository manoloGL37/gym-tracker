# Frontend-backend integration plan

## Phase 1 — authentication foundation (implemented)

- Angular standalone HTTP uses `provideHttpClient` and a functional JWT interceptor.
- Development calls `http://localhost:8080`; production calls `https://gym-tracker-api-s70k.onrender.com`. Authentication services obtain the URL from the Angular environment, never from duplicated literals.
- `AuthApiService` implements the documented authentication endpoints: registration, login, refresh, logout and `/api/users/me`. Login, refresh and logout opt into `withCredentials`; ordinary API and third-party requests do not.
- The access JWT lives only in the `AuthSessionService` in-memory signal and is attached as `Authorization: Bearer` to this backend's protected requests. It is no longer written to `localStorage`; startup removes the legacy auth key. The refresh token remains exclusively in the backend-issued, browser-managed `HttpOnly` cookie and is never read or copied by Angular.
- Startup begins in an explicit `checking` state and the application shell waits behind a session-restoration screen while one coalesced refresh loads a new in-memory access JWT and `/api/users/me`. Refresh `401` means an invalid session and returns to guest mode. Network/5xx errors remain `checking`, preserve local data and offer retry without flashing guest/login UI; a longer pending request explains that the server may still be starting.
- A protected-request `401` performs one coalesced refresh. All concurrent failures wait on the same in-flight promise, then retry their original request once with the rotated access JWT. A request that failed with a stale token after another refresh reuses the already-current token instead of rotating again. Login, refresh, logout and public calls bypass this behavior, and a retry marker prevents loops.
- Refresh `401` clears only the frontend authentication state and sends the user to login. Refresh network/5xx failures propagate as temporary errors without logging out. Logout calls the backend with credentials, then clears frontend auth in `finally`, navigates to login and never touches Dexie, migration ledgers, backups or local settings.
- Without an authenticated account, the application persists user data through the existing Dexie repositories and remains fully usable. This storage mechanism is not presented as a separate product mode.
- After login or successful session restoration, supported legacy data synchronizes automatically with the authenticated account. Authentication never clears or rewrites a local resource.
- Registration creates the account only, then sends the user to login as required by the API contract. Login allows the refresh cookie to be established, retains the returned access token in memory and loads `/me`.

## Phase 2 — cloud exercise catalog (implemented)

- Cloud exercises are isolated in `src/app/exercises`; their API DTOs are never assigned to the existing Dexie routine/workout shapes.
- `ExerciseApiService` calls the authenticated exercise catalog with the contract's custom page response (`content`, `page`, `size`, `totalElements`, `totalPages`) and server-side `search`, `category`, `equipment`, `muscleGroup` and `targetMuscle` filters.
- Filter selects load their real values from authenticated `GET /api/exercises/filter-options`; the page never guesses values from a partial catalog page. If that metadata request is unavailable, the catalog stays usable with the same server-side text filters.
- The server UUID is the cloud identity. Dataset exercises retain `(source, sourceId)` as their stable external identity. Names and aliases are display-only and are never used for local migration or matching.
- New custom exercises receive one native `crypto.randomUUID()` client ID when their draft opens. The ID remains in the draft after an error, so a retry reuses it.
- The catalog uses the current frontend language when choosing a backend translation, then falls back to English and finally the first server translation. Editing retains translations not shown in the form.
- `editable` and `deletable` are the only UI action permissions; no source/name heuristic enables them.
- Guests do not call the protected catalog and keep all local exercise/routine/workout functionality. Authenticated catalog operations are cloud-backed, but local routines and history are deliberately untouched.

## Phase 3 — cloud routines (implemented)

- `RoutineApiService` implements only the documented authenticated routine endpoints: Spring Page listing, detail, POST, full-replacement PUT and DELETE. Its DTOs in `src/app/routines/routine-api.models.ts` remain separate from the Dexie `Routine` shape.
- The routine screen presents one routine list without persistence badges. Guests use Dexie; authenticated sessions normally use account-backed routines while still showing compatible pending legacy routines. A failed/cold backend request keeps the readable legacy representation available.
- Guest create/edit/delete remains Dexie-only with the existing free-text exercise name and `setsCount` model. Authenticated new routines are cloud routines, require catalog-selected server exercise UUIDs, and send backend fields `sets`, `targetReps`, `restSeconds` and optional `notes`/`description`.
- The cloud exercise picker delegates to `ExerciseApiService`, uses server-side search and pages of 10. It displays the localized catalog name plus global/custom source, but uses only the server UUID as the submitted identity.
- Cloud routine positions are rebuilt explicitly from the editor array as contiguous 0-based values on every POST/PUT. This avoids stale or duplicate positions after removal; no exercise is matched by name.
- A cloud draft gets one `crypto.randomUUID()` `clientId`. A failed POST retains that draft and therefore reuses the same ID on retry. A successful save resets the editor, so the next new draft receives a new ID. PUT sends the contract's replacement DTO but the backend retains its original `clientId`.
- Automatic synchronization can create an account-backed equivalent for a compatible legacy routine. The ledger mapping then suppresses its legacy card in authenticated views without deleting or retyping the Dexie row. Existing selected-routine records lacking the internal marker continue to mean Dexie-backed, and no Dexie ID is ever used in an API URL.
- The local routine model has no backend equivalents for free-text exercise identity and only stores `setsCount`; cloud routines additionally require an exercise UUID, target reps, rest seconds and notes. These incompatible fields are intentionally not transformed between stores.
- Existing local routines can still start the existing local training flow unchanged. Phase 4 adds cloud selection separately; the local free-text/Dexie model is still never transformed into a cloud resource.

## Phase 4 — cloud workouts (implemented)

- `WorkoutApiService` implements only `GET /api/workouts`, `GET /api/workouts/{id}`, `POST /api/workouts`, `PATCH /api/workouts/{id}` and `POST /api/workouts/{workoutId}/exercises/{workoutExerciseId}/sets`. DTOs in `src/app/workouts/workout-api.models.ts` mirror the contract and remain distinct from Dexie history.
- Routine selection combines pending legacy and authenticated account routines as one product list. The internal `source` discriminator still routes to the correct repository. Account-backed selection stores the routine UUID, label and one generated workout `clientId`; the training screen creates the workout from the server routine snapshot. It never reconstructs workout-exercise IDs or identifies exercises by name.
- Cloud active state uses a separate small Dexie `cloudActiveTraining` cache. It contains the server workout/exercise identities plus editable set drafts for navigation/reload recovery. On an authenticated reload it refreshes the server workout and preserves only drafts the server has not already confirmed. It is not an offline sync queue and backend responses remain authoritative for persisted fields.
- A set starts as an editable local draft. Its `clientId` is generated once; retrying the same Save reuses it. `setNumber` is allocated deterministically from all existing drafts/sets and is 1-based. After the API confirms the set it becomes read-only because the backend has no edit/delete set endpoint. Weight, reps and optional RPE are sent exactly as documented.
- Cloud completion calls `PATCH { completed: true }`; the server supplies `completedAt`, preserving `startedAt`. The UI treats only `completedAt === null` as unfinished. It will not complete while a non-empty set draft is unsubmitted. A 401 or network failure leaves the local cloud resume cache and drafts untouched.
- Backend `LocalDateTime` is serialized by `toBackendLocalDateTime`: a local wall-clock ISO value with no offset or `Z`. The app does not apply a UTC convention the backend does not declare.
- Calendar presents one history without persistence labels. Internally it combines pending/unsupported Dexie history with one paginated account page, suppressing mapped legacy duplicates. The query parameter remains an internal detail-routing discriminator. A failed account request keeps readable Dexie history available. Account-backed details use saved fields, including RPE and snapshot exercise notes, and intentionally do not expose edit/delete actions unsupported by the API.
- Workout-level cloud notes can be saved when non-empty through the documented PATCH. The API cannot clear notes. Existing local per-exercise observations retain their local behavior; cloud has no corresponding user-observation field, so the screen shows snapshot routine-exercise notes and does not pretend observations are cloud-backed.
- Compatible historical workouts are synchronized automatically after their routine dependencies are confirmed. Names are never auto-matched and no historical Dexie workout is deleted.

## Phase 5 — cloud statistics (implemented)

- `StatisticsApiService` implements only the authenticated backend routes `GET /api/statistics/summary`, `comparison`, `evolution` and `exercises/{exerciseId}`. Its strict DTOs live in `src/app/statistics/statistics-api.models.ts`; they include every documented non-null aggregate, evolution point and required query parameter. The API has no duration or body-weight statistic, so neither is invented in the cloud model.
- For unauthenticated use, the statistics screen keeps Dexie's existing workout semantics: completed history is filtered by `finishedAt` in the selected week/month and derives session, set, repetition and `weight * reps` volume totals. Its charts contain only actual activity dates. Legacy exercise history retains its free-text/name grouping; its max weight and estimated 1RM are not account aggregates.
- Authenticated users automatically receive account-backed statistics as the authoritative summary. The screen obtains current/previous totals and percentage changes from `comparison`. Daily `evolution` points feed the selected-period volume chart; a user-selected ISO-week interval is requested as inclusive Monday/Sunday `from/to` dates and grouped into real weekly volume points. Weeks without observations are not invented. A successful zero response is an empty state, never an error.
- There is no persistence-source selector or label. Guest and authenticated totals are never blindly summed, avoiding double counting while synchronization is pending. A temporary account failure renders a retryable error rather than treating unavailable data as an empty result or logging the user out.
- Statistics dates are sent exactly as local calendar `YYYY-MM-DD` values. The API interval is inclusive (`from` through `to`) and based on backend local date/time semantics, so the client does not convert them to UTC or append an offset. Week means Monday–Sunday and month means its calendar bounds, matching the pre-existing UI selector.
- Per-exercise account statistics search the existing backend catalog, retain the selected server UUID as identity and pass only that UUID in the statistics URL with the same selected week interval. Daily endpoint observations are grouped per ISO week: volume is summed and maximum weight keeps the real weekly maximum. Localized names are display data and legacy free-text exercise names are never auto-mapped. Zero-valued aggregates with `evolution: []` are a successful no-data state.
- Body weight remains Dexie-only. There is no server persistence/statistics endpoint in the contract, and logout/401 do not remove body-weight entries.
- Completing an account-backed workout continues to call the Phase 4 documented completion PATCH. Statistics are re-fetched when the authenticated statistics screen loads or its period is selected; no frontend aggregate is mutated optimistically.

## Remaining work

- Backend support for arbitrary historical workout snapshots, per-exercise observations, active local workouts and body weight before those records can become cloud resources.
- A distinct cloud exercise-statistics browsing UX if product needs it; it must select catalog UUIDs and cannot reuse the legacy name-grouped history view.
- Offline queueing/conflict resolution only if product requirements justify it; no generic sync infrastructure is present.

## Visual redesign (completed)

- The Angular UI uses the shared “rubber, steel & chalk” visual foundation: a mobile-first training action, consistent surfaces and form controls, product-level synchronization wording, and tabular workout metrics. Internal API/Dexie distinctions remain intact but are not normal user-facing concepts.

## Phase 6 — automatic account synchronization (implemented)

- Successful login and successful startup session restoration start or resume synchronization in the background. Registration follows the backend contract and only creates the account; synchronization begins after the subsequent login. There is no confirmation, postponement action, or full-screen workflow. No operation deletes, clears, mutates, or replaces legacy Dexie records or backups.
- Dexie v7 adds `migrationLedgers`, one ledger per stable `/api/users/me.id`. It stores status, stable conversion defaults, generated client IDs, resource mappings, errors and unsupported reasons. A different account on the same browser receives a separate ledger and never reads/reuses another account's server UUID mappings.
- The persistence audit is: routines and their exercise references are **migratable with explicit transformation**; historical workouts are **conditionally migratable with transformation** only if their original routine exists, its exercise snapshot is identical, and all sets are valid. Active local training, exercise observations, body weight, backups, device metadata, language/UI settings and selected routine are **not currently migratable**. There is no separate persisted legacy custom-exercise entity; local free-text references are explicitly resolved.
- Names and aliases are never identity. Every unresolved legacy exercise identity requires an explicit catalog selection or explicit personal-exercise creation. Shared local UUIDs reuse one mapping; equal names with distinct UUIDs remain separate. Custom exercise client IDs and returned UUID mappings persist before dependent routines synchronize. Unresolved references block only their dependent records; independent resources continue.
- Local routines lack target reps/rest/notes/description. Settings exposes confirmed target-reps/rest defaults (initially 10/90); name, order and `setsCount` transfer. A routine with an unresolved dependency is blocked whole, never partially uploaded.
- Compatible history posts domain `startedAt`/`finishedAt` using the existing zone-less LocalDateTime serializer, then creates sets with persisted stable client IDs. Per-exercise observations remain available even though the API cannot persist them. Incomplete, orphaned or changed snapshots are marked unsupported instead of being distorted.
- A mapped resource becomes migrated only after the POST response confirms it. Retrying preserves client IDs and mappings, so partial failures resume without undoing successes. Authenticated routine and calendar views hide their mapped legacy counterpart; logout/guest use sees the untouched physical Dexie records.
- Body weight remains Dexie-only. Active training is deliberately deferred until the user finishes it locally. Backups remain untouched.
- `AccountSyncService` owns non-blocking orchestration and product-level status. Network errors, timeouts, `408`, `429`, and `5xx` keep records pending. Retry uses exponential delays capped at 60 seconds, and an `online` event retries immediately. Logout stops the coordinator but preserves every ledger and local row.
